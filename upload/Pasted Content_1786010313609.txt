# QuickQuid Engineer Wireframe and Product Specification

Status: Product blueprint for the v0.1 clickable prototype and engineering handoff.

Audience: Product engineer, frontend engineer, backend engineer, QA, operations lead, and product designer.

Out of scope: Tech-stack selection, API vendor selection, legal/tax advice, and production security architecture.

## 1. Product Contract

QuickQuid is a Buyer-to-Pro freelance marketplace built around trust, reputation, repeat hiring, and controlled manual operations.

### 1.1 Non-negotiable v0.1 rules

| Rule | Product requirement |
|---|---|
| Pro commission | QuickQuid deducts ₹0 platform commission from the Pro's agreed professional fee. |
| Buyer fee | Buyer pays a separate 14% beta QuickQuid fee on top of the Pro fee. |
| Fee visibility | Pro fee, Buyer fee, applicable-tax placeholder, and Buyer total appear before payment. |
| Payment model | Buyer submits structured payment evidence; Finance Admin verifies it manually. |
| Escrow/wallet | Do not claim automated escrow. Do not create a wallet in v0.1. |
| Work gate | A Pro cannot begin work until the required milestone is Payment Confirmed. |
| Payout model | Buyer acceptance creates Payout Queued; Finance/Admin then processes it manually. |
| Milestones | Maximum four milestones per contract. |
| Trust labels | Use identity reviewed, portfolio reviewed, availability, and completed projects. Never use an unexplained generic verified badge. |
| v0.2 | Productized Pro gigs are future overlays, not live v0.1 functionality. |
| v0.3 | Paid priority gig feed is future only. |

### 1.2 Canonical product actors

| Role | Uses the product for | Cannot do |
|---|---|---|
| Visitor | Choose intent and view public content | View private data or transact |
| Buyer | Find talent, post briefs, hire, pay, review, rehire | Access Admin controls or Pro payout data |
| Pro | Build profile/reputation, apply, work, deliver, receive payout | Access Buyer payment evidence or Admin controls |
| Support Tier 1 | KYC intake, support, workroom visibility | Move money or suspend users |
| Finance Tier 2 | Verify payments, process payout/refund records | Suspend users or decide risk cases |
| Risk Tier 3 | Review risk, disputes, suspensions, audit log | Verify payments or trigger payouts |
| Ops Manager | Watch queues/SLA and assign escalations | Bypass configured financial authorization |

## 3. Wireframe Convention

Every primary screen contains:

1. Who, What, When, Where, Why, and How.
2. Desktop-first text wireframe.
3. All required sub-screen/modal/drawer states.
4. Connections to prior and next states.
5. Data, permission, validation, and edge-condition rules.

Frame naming:

~~~text
[Role] / [Screen ID] / [Sub-screen ID] / [State] / [Viewport]
Example: Pro / S01 / 1.12 / Published / Desktop
~~~

## 4. SCREEN 01 - Account, Role, Profile and Verification Readiness

### 4.1 5W1H

- **Who:** Visitor, Buyer, Pro, authorized KYC/Risk Admin.
- **What:** Account creation, intent selection, personal/company profile setup, public preview, verification readiness, and payout-readiness setup.
- **When:** First visit; profile update; Pro eligibility setup; payout-data change.
- **Where:** Public entry, authenticated Settings/Profile, and Admin KYC queue.
- **Why:** QuickQuid needs clear role intent, credible profiles, controlled trust signals, and safe payout readiness without making Buyers abandon before seeing value.
- **How:** User selects role, authenticates, completes role-specific profile tasks, submits required information for review, receives clear status, and publishes a public profile.

### 4.2 Desktop wireframe

~~~text
[QuickQuid] [Role badge]                              [Help] [Bell] [Avatar]
--------------------------------------------------------------------------------
[Sidebar] | Breadcrumb: Account / Profile
          | [Page title]                         [Profile completion 72%]
          |
          | [Readiness cards / profile editor / verification step content]
          |
          |                           [What you can do next]
          |                           [Public vs private visibility summary]
~~~

### 4.3 Sub-screen specifications

#### 1.1 Role Selection

Who: Unauthenticated Visitor.  
What: Intent page with Buyer and Pro selection before authentication.  
When: First visit or intentional role registration.  
Where: Public root route.  
Why: Prevents mixed intent and sets the right dashboard/navigation.  
How: Two large cards: I want to hire and I want to work; Google, LinkedIn, or email authentication. Pro card says 0% QuickQuid commission. Keep 100% of your agreed professional fee.  
Connection: Success goes to 1.2. Authentication error stays inline with retry.

#### 1.2 Readiness Dashboard

Who: Buyer and Pro.  
What: Role-specific eligibility checklist and completion status.  
When: First login and whenever eligibility changes.  
Where: Dashboard onboarding section and Settings.  
Why: Shows what blocks a risky action without blocking exploration.  
How: Buyer tasks are account, profile, billing when needed, create brief, fund milestone. Pro tasks are profile, identity, evidence, payout details, Admin review, proposal eligibility. Buyer can browse and draft before verification.  
Connection: Card CTAs lead to 1.3, 1.8, 1.11, 5.1, or 6.3.

#### 1.3 KYC and Payout Upload

Who: Pro; Buyer only when policy requires it; authorized Admin reviewer.  
What: Multi-step identity and payout-information intake.  
When: Pro onboarding, payout setup, or re-verification.  
Where: Settings modal/dedicated onboarding step and Admin KYC queue.  
Why: Payout cannot safely occur without current reviewed payout information.  
How: Identity, professional details, payout details. Accept JPG/PNG/PDF up to 10MB. Mask sensitive fields after entry. Submit creates Pending Admin review.  
Connection: Submit goes to 1.4; Admin approval goes to 1.13; rejection returns to 1.4 resubmit.

#### 1.4 Pending and Rejected Verification

Who: Buyer/Pro who submitted information.  
What: Verification status and recovery state.  
When: After submission or Admin decision.  
Where: Readiness dashboard, Settings, notification deep link.  
Why: Users need a reason and self-service next step rather than a vague failed state.  
How: Pending shows target review time. Rejected shows configured reason and Resubmit CTA.  
Connection: Resubmit goes to 1.3. Support goes to 99.2.

#### 1.5 Pro Payout-Readiness Interlock

Who: Pro.  
What: Blocking modal when a Pro attempts a paid proposal while payout readiness is incomplete.  
When: Pro presses Submit Proposal in 6.3.  
Where: Proposal modal overlay.  
Why: Avoids accepting work where payout cannot be completed.  
How: Modal identifies the missing requirement with Add payout details and Cancel; do not erase the draft proposal.  
Connection: Add payout goes to 1.3; approval later returns to preserved proposal draft.

#### 1.6 Duplicate Device/Network Risk Flag

Who: Risk Admin.  
What: Risk signal attached to a verification record.  
When: A risk rule detects a match with a prior suspended pattern.  
Where: Admin KYC record header.  
Why: Manual review needs investigation support without treating a match as automatic guilt.  
How: Show hashed signal, match confidence, prior status, history, and actions: Investigate, Request information, Reject, Approve with documented rationale.  
Connection: Decision creates 12.4 audit event and 99.1 notification.

#### 1.7 Update Payout Details

Who: Pro.  
What: Edit/re-verification flow for payout data.  
When: Pro changes beneficiary/bank details.  
Where: Pro Settings > Payout details.  
Why: Payout destination changes are high-risk.  
How: Save changes as pending, mask data, pause new paid proposals until review. Existing contractual obligations stay visible to Admin.  
Connection: Submit to 1.4; Admin decision updates 1.13.

#### 1.8 Buyer Organization Details

Who: Buyer.  
What: Private billing/company information editor.  
When: Buyer enters or updates invoice/billing context.  
Where: Buyer Settings > Organization and billing.  
Why: Company details need correction without Support intervention.  
How: Company name, billing address, GSTIN if applicable, billing contact, validation, save state. It does not alter public profile automatically.  
Connection: Data is used by 5.1, 8.1, and 11.7.

#### 1.9 Terms and Privacy Consent

Who: Buyer and Pro.  
What: Explicit commercial-terms and privacy-notice acknowledgement.  
When: Before sensitive verification submission and account activation.  
Where: KYC completion modal.  
Why: User sees fee terms and information-use notice at the point of action.  
How: Separate checkboxes for Terms including fee structure and Privacy Notice; record version/timestamp.  
Connection: Required before 1.3 submission.

#### 1.10 Pro Work Relationship Acknowledgement

Who: Pro.  
What: Commercial relationship acknowledgement.  
When: During Pro verification/onboarding.  
Where: KYC final step.  
Why: Establishes user understanding while legal terms remain governed by an approved agreement and law.  
How: Show counsel-approved acknowledgement text and record version, time, and user ID. Do not treat this as legal classification by itself.  
Connection: Required before 1.3 submission.

#### 1.11 Personal Profile Builder

Who: Buyer and Pro.  
What: Edit personal/company profile and reputation surface.  
When: Onboarding and later profile updates.  
Where: Settings > Profile and readiness CTA.  
Why: Marketplace users need credible, comparable information to decide.  
How: Pro fields: avatar, public name, headline, bio, categories, skills, portfolio, work samples, availability, response time, project size, optional language/time-zone. Buyer fields: display name, logo, company description, industry, hiring categories. Each field shows public/private setting.  
Connection: Save goes to 1.12; published profile appears on 3.1 and 4.1.

#### 1.12 Public Profile Preview and Customization

Who: Buyer and Pro.  
What: Exact public-profile preview plus customization.  
When: Before publishing or adjusting visibility.  
Where: Settings > Profile > Preview.  
Why: Users must know what another marketplace user will see.  
How: Reorder sections, choose featured portfolio item, set optional field visibility, preview by role, save draft, publish/unpublish. Trust labels are dimensioned.  
Connection: Publish appears in 3.1 Discovery and 4.1 Detail; unpublish removes discovery eligibility but preserves contracts.

#### 1.13 Profile Completion and Approval Interlock

Who: Buyer and Pro.  
What: Eligibility status derived from profile, evidence, verification, and payout readiness.  
When: Any supporting state changes.  
Where: Dashboard, Profile settings, proposal submission, public profile.  
Why: Converts opaque eligibility into a clear checklist.  
How: Show required versus optional tasks and why access is locked. Never reveal private risk logic.  
Connection: Enables 3.1 publication, 6.3 proposal, and payout functions by role.

### 4.4 Screen 01 rules

- Public profile visibility is separate from account privacy and billing data.
- Sensitive KYC/payout fields never render on public profile frames.
- Profile changes have draft, saved, and published states; contracts preserve their original profile snapshot.
- Pro payout changes trigger re-review and proposal eligibility interlock.
- Every Admin review action writes an audit event.

Why: Prevents missed payment evidence, blocked work, and unreviewed delivery.

#### 2.4 Global Notification Drawer

Who: Buyer and Pro.  
What: Global event list.  
When: User opens Bell or system adds event.  
Where: Header right-side drawer.  
Why: User should not poll multiple pages for updates.  
How: Ordered notifications with unread state, timestamp, entity name, event summary, deep link, mark-read.  
Connection: Every notification opens the precise entity/sub-screen.

### 5.4 Screen 02 rules

- Derive dashboard cards and banner from the canonical state model; do not create a second conflicting status system.
- The most urgent blocking item wins banner priority.
- Dismissing a notification never resolves the underlying requirement.

### 14.4 Screen 11 rules

- Dispute state freezes only the relevant payout/review activity; system should clearly show what is paused.
- Admin decision and money movement are separate: Risk resolves outcome, Finance executes payout/refund under permission controls.

- Tax, invoice, ownership, defect, and dispute-finality language must be configurable/counsel-approved before production.

## 18. Engineer Build Acceptance Checklist

### Product logic

- [ ] Pro never appears to pay QuickQuid a platform commission.
- [ ] Buyer sees 14% fee before publishing/offer/payment.
- [ ] Payment evidence submitted is distinct from Payment Confirmed.
- [ ] Pro cannot begin work before Payment Confirmed.
- [ ] Buyer acceptance queues payout; it does not claim instant transfer.
- [ ] No v0.1 wallet or automated escrow language exists.
- [ ] Maximum four milestones is enforced and explained.
- [ ] v0.2 gigs are visibly separated from live v0.1 routes.

### Permissions and data

- [ ] Buyer, Pro, Support, Finance, Risk, and Ops see only their allowed controls.
- [ ] Public profile never renders sensitive payout/KYC/billing/risk data.
- [ ] Admin sensitive-data reveal requires authorization/reason/audit event.
- [ ] Risk decision and Finance money execution are distinct permissions.
- [ ] Every Admin action creates an audit event.
- [ ] Existing contract snapshots survive profile/brief edits.

### UX states

- [ ] Every primary screen has default, loading, empty, validation error, permission denied, pending, success, rejected/recovery, SLA warning, and mobile variants where relevant.
- [ ] Every blocking state has explanation and recovery path.
- [ ] Every financial event has reference ID, timestamp, and user-facing next action.
- [ ] Notifications deep-link to the exact record and current state.
- [ ] Mobile does not hide price, warnings, or primary CTA.

- [ ] New Buyer with no projects.

5. Cancellation, refund, defect-window, IP, and dispute-resolution contract language.
6. Data retention/export/deletion policy.
7. Payment rail, bank instructions, payout batch format, and reconciliation method.
