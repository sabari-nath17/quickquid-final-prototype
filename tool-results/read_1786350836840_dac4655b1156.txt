   111→## Visual Direction
   112→
   113→Create a premium editorial-meets-operational design. It should feel credible enough for a serious B2B product but approachable enough for a first-time small-business Buyer.
   114→
   115→### Subject lock
   116→
   117→Design from QuickQuid's actual world, not from generic marketplace references:
   118→
   119→- **Subject:** accountable execution of digital freelance projects.
   120→- **Primary audience:** an owner or product lead who needs work completed without becoming the project manager.
   121→- **Secondary audience:** a skilled independent professional who wants clear scope, realistic commitments and fair acceptance.
   122→- **Landing-page job:** make a Buyer understand the execution difference and begin project readiness.
   123→- **Product-app job:** make the next decision, owner, evidence and money state obvious.
   124→
   125→Use the visual language of working agreements, delivery evidence, project clocks, change records and financial ledgers. Do not use generic creator-economy imagery or an endless marketplace grid as the main identity.
   126→
   127→### Design language
   128→
   129→- **Field Paper `#F3F5F2`:** cool neutral page canvas; avoid the fashionable cream-and-terracotta look.
   130→- **Surface `#FFFFFF`:** cards, forms and raised decision layers.
   131→- **Working Ink `#141715`:** primary text and high-confidence actions.
   132→- **Execution Green `#0B8F63`:** completed, accepted and healthy states.
   133→- **Forecast Indigo `#4E62D8`:** scheduled, in-progress and informational states.
   134→- **Attention Ochre `#B46D0A`:** action required and approaching deadlines.
   135→- Use **Exception Red `#C43F39`** only for blocked, failed, destructive or disputed states.
   136→- **Display type:** Sora, 600–700 weight, used only for major headlines and decisive section statements.
   137→- **Body type:** Source Sans 3, 400–600 weight, optimised for forms, explanations and longer project records.
   138→- **Utility/data type:** IBM Plex Mono, 500 weight, used sparingly for Q₹ amounts, project references, dates and immutable event IDs.
   139→- Provide robust system-font fallbacks if these web fonts cannot load.
   140→- Desktop content width: 1200–1280px.
   141→- Card radius: 14–18px. Button radius: 10–12px.
   142→- Use a restrained shadow system. Avoid excessive floating cards.
   143→- Use clear status icons from one consistent icon library.
   144→- Do not use emoji, fake customer logos, generic stock photos, decorative gradients or oversized empty areas.
   145→- Use real-looking sample project thumbnails or generated product-work visuals. Label every invented example as **Sample project**.
   146→
   147→### Layout concept
   148→
   149→Use an **operational editorial layout**:
   150→
   151→- Landing hero: concise thesis on the left, live execution artifact on the right.
   152→- Marketing sections: broad horizontal bands with strong typographic hierarchy, not a pile of identical cards.
   153→- Dashboards: one dominant next-action region followed by lower-priority operational detail.
   154→- Workroom: evidence and conversation in the main column; forecast, funds and acceptance in a narrower decision rail.
   155→- Mobile: one linear decision path with the next action first.
   156→
   157→Dividers, labels, sequence markers and numbering must encode real project structure. Only number steps that must happen in order.
   158→
   159→### Signature element: the Execution Spine
   160→
   161→The one memorable visual device is the **Execution Spine**: a compact, vertically connected record of the project moving through Ready, Proof Match, Capacity Lock, Pact, funded milestone, First Proof and accepted delivery.
   162→
   163→Each Spine event shows only information that proves execution:
   164→
   165→- State and plain-language label.
   166→- Responsible actor.
   167→- Timestamp or forecast.
   168→- Evidence or decision reference.
   169→- Q₹ state when money is affected.
   170→
   171→Use the Execution Spine in the hero sample, project workroom and completion record. It should feel like the project's living operational record, not a decorative timeline.
   172→
   173→This is the single deliberate aesthetic risk: project evidence becomes the visual identity. Keep the rest of the interface quiet enough for it to remain distinctive.
   174→
   175→### Design philosophy: Operational Flat+
   176→
   177→Use **Flat 2.0 / Flat+** as the foundation. The interface should remain clean, fast and scalable, while using selective depth to make actions, hierarchy and state changes unmistakable.
   178→
   179→Core rule:
   180→
   181→> **Flat structure. Visible affordance. Selective depth.**
   182→
   183→QuickQuid handles scope decisions, milestone acceptance and simulated money movement. Pure flat design would make some controls look like ordinary content. Add depth only when it helps the user understand what can be clicked, what needs attention or which layer is currently active.
   184→
   185→#### Elevation system
   186→
   187→Use four deliberate levels:
   188→
   189→- **Level 0 — Page:** flat background, sections and data tables. No shadow.
   190→- **Level 1 — Interactive surface:** selectable project cards, Pro cards and inputs. One-pixel border with a very soft shadow or tinted hover state.
   191→- **Level 2 — Priority action:** next-action card, funding confirmation and delivery review. Slightly stronger shadow and contrast.
   192→- **Level 3 — Temporary layer:** dialogs, drawers, menus and confirmation sheets. Clear overlay, strongest shadow and visible close action.
   193→
   194→Do not add shadows to every card. Static information should usually remain flat.
   195→
   196→#### Component affordances
   197→
   198→- **Primary buttons:** filled ink or brand colour, clear label, optional directional icon and visible hover/pressed states.
   199→- **Secondary buttons:** bordered surface with clear hover tint.
   200→- **Tertiary actions:** text button with icon or underline on hover; never plain body text pretending to be clickable.
   201→- **Destructive actions:** red text or fill plus explicit confirmation; never colour alone.
   202→- **Inputs:** persistent label above the field, visible border, helpful example, clear focus ring and inline validation.
   203→- **Clickable cards:** show pointer behaviour through border, hover tint and a small directional cue. Static cards must not imitate this treatment.
   204→- **Tabs:** use label, active indicator and contrasting surface. Do not rely on a faint colour change.
   205→- **Status chips:** combine icon, text and colour.
   206→- **Dialogs and sheets:** use depth and background overlay because they represent a new decision layer.
   207→- **Tables:** mostly flat, with dividers, aligned columns, sticky headers and a row-hover state only when rows are interactive.
   208→
   209→#### Where depth should be strongest
   210→
   211→Use selective depth for:
   212→
   213→- The interactive sample execution record in the hero.
   214→- The single “next action” card on each dashboard.
   215→- Demo-credit funding and release confirmations.
   216→- Delivery acceptance and revision controls.
   217→- Change Card and dispute decisions.
   218→- Mobile navigation sheets and confirmation dialogs.
   219→
   220→Keep profiles, historical activity, FAQs, descriptions and read-only project information flatter.
   221→
   222→#### Hero treatment
   223→
   224→Keep the headline area editorial and mostly flat. Give the sample execution record controlled depth through two or three slightly overlapping surfaces, a soft ambient brand tint and crisp status indicators.
   225→
   226→Do not use glassmorphism, glossy liquid effects, heavy blur or ornamental 3D. The visual interest should come from useful project information becoming progressively clearer.
   227→
   228→#### Interaction states
   229→
   230→Every interactive component must include:
   231→
   232→- Default.
   233→- Hover.
   234→- Keyboard focus.
   235→- Pressed or selected.
   236→- Disabled with an explanation when necessary.
   237→- Loading.
   238→- Success or error when applicable.
   239→
   240→Motion should reinforce hierarchy: 120–180ms for buttons and cards, 180–240ms for sheets and dialogs. Avoid decorative looping animation.
   241→
   242→### Design checkpoint before implementation
   243→
   244→Before writing or changing UI code, produce a short internal design plan containing:
   245→
   246→1. The final colour tokens and their exact roles.
   247→2. The display, body and utility typography roles.
   248→3. The desktop and mobile layout logic.
   249→4. The Execution Spine behaviour.
   250→5. The single page-load motion sequence.
   251→
   252→Critique that plan against this test:
   253→
   254→> Could the same visual plan be dropped into an unrelated SaaS marketplace without meaningful changes?
   255→
   256→If yes, revise the generic part before building. Spend visual boldness on the Execution Spine, typography and evidence presentation—not on extra effects.
   257→
   258→After implementation, capture the landing page, intake, dashboard, workroom and demo-funding flow at desktop and mobile widths. Remove at least one unnecessary decorative treatment before finalising.
   259→
   260→### Responsive behaviour
   261→
   262→- Test at 375px, 440px, 768px, 1024px and 1440px.
   263→- No horizontal overflow.
   264→- On mobile, replace the permanent sidebar with a bottom navigation containing no more than five items.
   265→- Put secondary destinations inside a menu sheet.
   266→- The hero headline, explanation and primary action must all be visible inside the first mobile viewport.
   267→- Forms use one column on mobile and a form-plus-preview layout only from desktop widths.
   268→- Workroom tabs must be horizontally scrollable or collapse into a section selector.
   269→- Sticky actions must never cover fields, project cards or the help button.

   687→## Interaction Quality
   688→
   689→- One primary action per screen.
   690→- Show the next required action above historical activity.
   691→- Preserve data and state when switching roles.
   692→- Reset scroll to the top after route changes.
   693→- Autosave form progress and show `Saved just now`.
   694→- Use skeleton loading states instead of blank screens.
   695→- Use meaningful empty states with a next action.
   696→- Confirm destructive actions.
   697→- Use toast messages only for brief confirmations; important status changes remain visible on the page.
   698→- Make delivery, funding and dispute status understandable without opening another screen.
   699→- Use consistent terms everywhere: Buyer, Pro, project, milestone, Pact, Commit Date, Change Card, Project Clock and Definition of Done.
   700→
   701→### Interface writing system
   702→
   703→- Write from the user's side of the screen. Use names people recognise, not internal implementation terms.
   704→- Use active voice and plain verbs.
   705→- A control must name its result: `Lock Q₹25,000`, `Accept milestone`, `Request changes`, `Save brief`.
   706→- Keep action language consistent through confirmation: `Accept milestone` produces `Milestone accepted`.
   707→- Labels label, examples demonstrate and helper text explains. Do not make one line perform several jobs.
   708→- Errors state what happened and how to fix it. Do not use vague apologies.
   709→- Empty states explain what will appear and provide one useful next action.
   710→- Avoid marketing language inside the product app. Product UI should describe decisions and consequences.
   711→- Use sentence case. Reserve uppercase for short utility labels such as status categories.
   712→
   713→### Frontend implementation discipline
   714→
   715→- Define colour, type, spacing, radius, elevation and motion as shared tokens.
   716→- Build reusable primitives for buttons, fields, cards, status chips, tabs, dialogs, tables and the Execution Spine.
   717→- Avoid broad element selectors that override component classes.
   718→- Keep component variants explicit instead of stacking conflicting utility classes.
   719→- Do not fix responsive problems with arbitrary widths, negative margins or overflow hiding.
   720→- Use content-sized containers and CSS grid/flex rules that reflow intentionally.
   721→- Test long project names, large Q₹ amounts, validation messages and translated-length labels.

   728→- Provide visible keyboard focus rings.
   729→- Maintain logical heading order.
